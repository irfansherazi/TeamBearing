### Research question (answer this exactly)

> What HITL (human-in-the-loop) checkpoint designs exist for LLM-to-test-plan pipelines — specifically, what is the minimum viable review interface that allows a QA engineer to inspect, edit, and approve a structured test plan (JSON format) before execution, and what patterns have been validated in production tools or open-source projects?

### Why normal lanes may be insufficient

HITL in AI test generation is underexplored in academic literature; practitioner discourse is fragmented across Slack, Discord, and company engineering blogs. The target system already has a rich HITL subsystem (human_takeover_node, TakeoverPanel frontend component) that operates at *execution* time — but the design space for a *pre-execution* test plan review gate (after LLM compilation, before Playwright runs) is architecturally distinct and requires specific UX and data-flow patterns not covered by existing material.

### Required output shape

Produce a structured report with:

1. **Executive summary** (≤5 bullets) — no verdict language
2. **Prior art / systems table** — columns: Name | Type (paper/product/post) | Year | URL or DOI | Relevance (1 line) | Design pattern used | Reported limitations or failure modes
3. **Design pattern catalog** — for each identified HITL checkpoint pattern:
   - Pattern name
   - Where in the pipeline it intercepts (pre-compilation / post-compilation / post-execution)
   - UI approach (diff view, structured form, natural language correction, inline edit)
   - Data model (what does the reviewer see and what can they change?)
   - Integration complexity (how does the corrected output re-enter the pipeline?)

### Spike context (do not re-research these — background only)

**Research objectives**
- Reduce uncertainty around which HITL checkpoint design is most likely to close vQA's quality gap between AC parsing and test execution
- Identify minimum viable review UI patterns that fit an existing LangGraph + React architecture

**Related lane findings (incorporating codebase and docs lane results)**

The vQA system uses LangGraph with AWS Bedrock. Key findings from parallel research:
- LangGraph `interrupt_before=["executor_node"]` already supports pre-execution interruption with no new node type required — resume via `Command(resume=user_response)` with same `thread_id`
- A pre-parse HITL checkpoint exists (`ac_parser_node` blocks on asyncio.Event for "fair" AC quality) but there is NO post-compilation checkpoint between JSON Compiler output and Playwright execution
- The existing `TakeoverPanel.tsx` (frontend) handles execution-time takeover — the design space for a *test plan review* UI (structured JSON diff, field-level editing, approve/reject) is new territory
- The compiled TestPlan JSON schema includes: `steps[]` (each with `action`, `target_component`, `verification`, `step_type`), `test_name`, `description`
- The quality gap is primarily in Stage 2 (JSON Compiler): incorrect `step_type`, hallucinated `target_component`, missing `verification` fields
