### TRAP Candidates

**TRAP-DR-001: Few-shot static exemplars may degrade performance for complex test cases.**
arXiv:2407.00225 found FSL consistently underperforms ZSL and CoT for Java unit test generation across all four models evaluated. The FSL gain reported in other studies is domain-specific (Gherkin from user stories in arXiv:2504.07244) and depends on exemplar quality and task similarity. Adding static few-shot examples to JSON_COMPILER_PROMPT without validation against the Golden 10 benchmark risks regression. Mitigation: use dynamic few-shot (DSPy BootstrapFewShot) rather than static exemplars, or validate each exemplar against the benchmark before adding.

**TRAP-DR-002: Constrained decoding degrades reasoning accuracy by up to 27 pp if schema is enforced before chain-of-thought completes.**
Multiple sources confirm (tianpan.co, SOB arXiv:2604.25359) that forcing schema structure prematurely prevents the model from completing necessary reasoning steps. If Bedrock tool-use is applied to Stage 2 without adding a prior free-form reasoning step, semantic accuracy of the generated test plan (correct step_types, verification assertions) may worsen even as structural JSON compliance improves. Mitigation: add an optional `reasoning` scratchpad field to the output schema; this field should be emitted FIRST before the `steps` array.

**TRAP-DR-003: Schema compliance does not equal value accuracy — a persistent silent failure mode.**
SOB (arXiv:2604.25359) demonstrates that even the best models achieve only 83% value accuracy on text, despite near-perfect schema compliance. vQA's `_repair_json` and retry loop solve structural compliance but do not detect semantic errors (wrong step_type, invalid target_component, hallucinated verification). Without a Stage 2 output quality gate, schema-valid but semantically wrong plans execute silently. This is flagged as TRAP-6 in the codebase lane and is independently confirmed by multiple academic sources.

**TRAP-DR-004: Self-consistency is not applicable at temperature=0.0.**
Self-consistency requires sampling diversity (temperature > 0). vQA's parser runs at temperature=0.0 (deterministic). Enabling self-consistency requires raising temperature, which introduces variability that may cause regressions in currently passing test cases. The cost is also 3–5x per invocation. This technique is lower-priority relative to prompt-structure changes.

**TRAP-DR-005: Evaluation dataset contamination inflates Golden 10 baseline accuracy.**
ULT benchmark research (arXiv:2508.00408) shows contaminated benchmarks report 91.79% accuracy vs 41.32% on uncontaminated equivalents — a 50 pp gap. The Golden 10 dataset uses real vSuite Jira tickets that may appear in Claude's training data. Any accuracy improvement measured against Golden 10 alone may be overstated. A hold-out set of novel, post-training-cutoff tickets is required for unconfounded evaluation.

### Open Questions

1. **What is vQA's current Stage 2 baseline accuracy on field-level correctness (step_type, target_component, verification type)?** The benchmark measures fuzzy step-text coverage, not JSON field accuracy. Without a field-level baseline, the improvement from prompt changes cannot be quantified. Extending `golden_10_data.json` with `expected_step_types` and `expected_verification_types` per step is the prerequisite for measuring any DRP-001 recommendations.

2. **Does adding an optional `reasoning` field to JSON_COMPILER_PROMPT output schema satisfy the downstream schema consumers?** The codebase lane identified 13+ consumers of `acceptance_criteria_steps`. An optional field at the `TestPlan` root level (not inside `StructuredACStep`) would be safe if consumers use `model.steps` directly. Needs verification against `schemas.py` Pydantic model to confirm optional field tolerance.

3. **Can Claude Haiku 4.5 (the actual parser model) benefit from chain-of-thought to the same degree as Claude Sonnet-class models?** Most academic evidence is from GPT-4 or Sonnet-class models. Haiku is a smaller, faster model — CoT gains may be smaller. The interaction between model tier and prompt technique is underexplored for Haiku specifically. A quick A/B test on the Golden 10 dataset with/without a reasoning field would answer this.

4. **What is the right evaluation metric for acceptance test plan quality?** Macro-recall (arXiv:2510.03641), helpfulness rating (arXiv:2504.07244), Mean Absolute Average Error (arXiv:2512.01232), and field-level JSON accuracy (SOB) are all plausible metrics. The right metric for vQA depends on whether "quality" means step completeness (coverage), semantic correctness (right component/action), or executability (steps the executor can run). This is the core open question in the Requirements ambiguity dimension.

5. **What few-shot exemplars exist in the vQA knowledge base that could be used for dynamic few-shot injection?** `backend/engine/ac_enricher.py` has a KB but it injects domain context, not example BDD/JSON pairs. The `knowledge/` directory and `BDD_COMPILER_PROMPT`'s `{blueprints}` slot suggest infrastructure exists. Are there existing correct (AC input, BDD output) or (BDD input, JSON output) pairs that could populate a few-shot library?

6. **Does Bedrock's tool-use API enforce schema compliance deterministically for Haiku 4.5?** DRP-002 covers this question — DRP-001 cannot answer it because the Bedrock-specific behavior under tool-use is out of scope for this literature probe. The answer from DRP-002 should be incorporated before implementing any tool-use enforcement on Stage 2.
