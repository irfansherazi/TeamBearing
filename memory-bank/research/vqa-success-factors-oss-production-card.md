### TRAP Candidates

1. **Playwright Test Agents (Healer) — undisclosed exit condition.** Healer loops "until resolution or guardrail activation" with no published step limit or guardrail definition. A healer with no budget in a CI pipeline could consume unbounded compute. Risk is high because it is a first-party Microsoft tool with the appearance of production-readiness.

2. **LangGraph recursion_limit config-merge bug (issue #7313).** Setting `recursion_limit` at compile time or in a shared config dict may be silently reset to 25 during config merging. Appears to work in development but fails at production invocation patterns. Closed as "not planned" (issue #6731 variant). Any vQA config that sets the limit outside the per-invocation `config={}` dict is vulnerable.

3. **ZeroStep per-call LLM cost model.** No native retry limit or budget cap in the `ai()` API. External retry wrappers without a cost ceiling can generate unbounded API charges at scale. Low adoption signal (361 stars) also means limited production hardening evidence.

4. **testRigor intent-based NLP — silent wrong-step generation.** The NLP layer that translates intent to steps does not expose a confidence score or ambiguity flag. The 27.22% human-review-required rate from the case study implies a significant fraction of generated steps are quietly incorrect. TRAP: using testRigor-style intent parsing without an ambiguity classifier produces confident-but-wrong test steps with no signal for human review.

5. **Applitools Eyes "99.9999% accuracy" claim.** The claim appears in vendor marketing with no cited methodology or sample size. The actual Visual AI architecture (screenshot → element decomposition → semantic comparison) is sound, but the specific accuracy figure is unverified. Adopting this tool based on the marketing metric without independent validation is a TRAP.

6. **LLM-as-judge single-turn rubric applied to multi-step tests.** Research (arxiv 2606.10315) shows a per-turn judge catches 0% of multi-step state-tracking defects in 100 rounds of evaluation. Any vQA verifier evaluating only the current step's screenshot — without session-level state context — replicates this failure mode exactly.

### Open Questions

1. **What is vQA's current LangGraph version?** If it is at or near 1.0.6, the infinite-loop regression (issue #6731) may be contributing to circuit-breaker fires independent of prompt quality or navigation strategy.

2. **Does vQA's recursion_limit apply at the per-invocation `config={}` level, or at compile/with_config level?** The config-merge bug makes this distinction production-critical.

3. **Does vQA's verifier evaluate per-step state only, or session-arc state?** The arxiv 2606.10315 finding suggests per-step-only evaluation misses the majority of real failures.

4. **Is there a `max_usd` or wall-clock budget axis in vQA's circuit breakers?** The step-count budget alone does not bound cost when steps involve expensive LLM calls.

5. **What is the measured false-positive rate of vQA's current verifier on known-passing and known-failing steps?** No empirical baseline was found externally — this must come from the Internal/Codebase lane.

6. **Does Reflect.run's per-run LLM consultation model scale to vQA's test suite size?** If vQA were to adopt a Reflect-style dynamic-resolution approach, the per-run LLM cost needs empirical benchmarking against the current approach.

7. **Is there a published no-progress detector pattern for LangGraph that hashes state between steps?** The practitioner heuristic (hash tool-call + arguments, terminate on repeat) needs a reference implementation to evaluate adoption effort.
