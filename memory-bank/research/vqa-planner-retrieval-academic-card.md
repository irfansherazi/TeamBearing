### TRAP Candidates

1. **Graph retrieval infra mismatch** — RANGER (arXiv 2509.25257) and CodexGraph (arXiv 2408.03910) demonstrate meaningful recall gains from graph-based retrieval but require Neo4j or equivalent graph database infrastructure. For vQA's 5-file helper corpus, the infra cost and maintenance burden may far exceed the benefit. A simpler import-list approach (LARGER-style) or static adjacency map may capture 80%+ of the graph benefit at near-zero cost — but this is not confirmed by benchmarks at vQA's small corpus scale.

2. **BM25/TF-IDF baseline weakness is Python-benchmarked, not TypeScript-benchmarked** — The largest measured recall gap (BM25 NDCG@10 = 29.79 vs dense 56.26, CoIR) is on a benchmark that includes JavaScript but does not specifically isolate TypeScript identifier matching. TypeScript identifiers (camelCase, PascalCase, typed function signatures) may have different lexical collision rates than Python, making the severity of the failure mode at vQA slightly uncertain.

3. **Dense embedding CPU latency is unmeasured in the literature** — No paper in the corpus (CodeXEmbed, voyage-code-2, CodeRAG-Bench, CoIR) reports per-query CPU inference latency for a ~200K-token corpus. The 400M CodeXEmbed variant and quantized sentence-transformers are cited as feasible but without benchmark numbers for the Docker/ECS/no-GPU constraint. This is a feasibility unknown that cannot be resolved from SOTA literature alone.

4. **Agentic retrieval risk** — SoK Agentic RAG (arXiv 2603.07379) formally identifies "retrieval misalignment" and "cascading tool-execution vulnerabilities" as systemic risks of ReAct-style tool-call retrieval. For vQA's planner (which already has tight per-loop node-count constraints), adding a per-step retrieval tool call could violate the ≤2-node-per-loop anti-pattern and introduce new failure modes.

5. **Fine-tuned routing outperforms generic classifiers, but training data is the bottleneck** — RAGRouter-Bench (arXiv 2604.03455) finds 93% routing accuracy with TF-IDF+SVM for complexity routing, but this is query-complexity routing, not per-module routing. Routing "this AC step → QO_helpers.ts" requires labeled examples pairing AC step text with module assignments — vQA has an existing golden-10 dataset but its size (10 runs) may be insufficient for reliable fine-tuning without data augmentation.

### Open Questions

1. **CPU inference latency for 400M dense model on vQA's corpus**: No paper in the academic corpus measured per-query embedding latency on CPU-only infrastructure for a ~200K-token TypeScript corpus. This must be empirically measured (DRP-001).

2. **TypeScript-specific BM25 failure rate**: All benchmarks are Python-dominant or multi-language with JavaScript (not TypeScript). The CoIR benchmark includes JavaScript but does not report per-language breakdowns. Whether the +26-pt NDCG gap between BM25 and dense embedding generalizes to TypeScript identifier queries is unconfirmed.

3. **Does LARGER-style graph expansion cause over-retrieval in a 5-file high-fan-in corpus?**: LARGER reports Acc@5 gains on SWE-bench repos with many files. When applied to a 5-file corpus where QO_helpers.ts is imported by most other helpers, transitive graph expansion may pull the entire corpus regardless of query, eliminating the precision benefit. No study examines graph retrieval at this small-corpus / high-fan-in configuration.

4. **AC-step-to-module routing accuracy at the specific vQA domain**: The RAGRouter-Bench result (93% TF-IDF+SVM routing) is for query-complexity routing with adequate labeled data. The analogous task for vQA (step text → helper module) requires a labeled dataset that does not yet exist beyond the golden-10 session JSONL. Pre-mapping classifier feasibility is plausible but unvalidated by any published study on this exact task framing.

5. **Index staleness maintenance cost per strategy**: No paper in the corpus specifically measures the re-indexing cost of dense embedding models vs BM25 when helper files change across sprints. The academic literature acknowledges this as a production concern but provides no quantified data.

6. **Hybrid fusion weight sensitivity**: Hybrid BM25 + dense retrieval studies show large aggregate gains but don't report sensitivity of recall to the sparse/dense fusion weight (alpha). If the optimal weight is highly corpus-dependent, self-tuning alpha on vQA's 5-file corpus may require more labeled queries than are available.
