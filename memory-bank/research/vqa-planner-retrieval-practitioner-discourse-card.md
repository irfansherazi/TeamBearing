### TRAP Candidates

- **Dense retrieval silently fails on function-name lexical mismatch, producing confident wrong retrievals with no error signal** — TianPan.co hybrid search post (https://tianpan.co/blog/2026-04-12-hybrid-search-production-bm25-dense-embeddings) (Grade C); a drop-in dense-only replacement for TF-IDF may not close the recall gap for function-name queries
- **ChromaDB first-retrieval cold-start latency reported at ~1 minute in production** — LlamaIndex GitHub issue #15201 (https://github.com/run-llama/llama_index/issues/15201) (Grade C); vQA on ECS (container restarts common) may present this to every first planner call after scale-up
- **CPU embedding inference at ~450ms/query on BERT-class models may crowd out vQA's 2s per-step budget when combined with LLM inference** — sbert.net efficiency docs (https://sbert.net/docs/sentence_transformer/usage/efficiency.html) (Grade C); no-GPU constraint makes this a hard ceiling rather than a tunable one
- **Voyage-code API latency described as "always best but also has high latency" — 20–50 API calls per vQA session compounds network latency materially** — HN Voyage-code-3 thread (https://news.ycombinator.com/item?id=42690818) (Grade C); API-based embedding inference may be incompatible with per-step latency budget
- **Index staleness is silent — stale embeddings score identically to fresh ones, producing confident wrong retrievals when helper files change across sprints** — HackerNoon staleness post + ranjankumar.in (Grade C); without a file-hash-triggered rebuild, the dense index silently rots
- **Embedding model version mismatch after upgrade invalidates all existing vectors without error** — ilovedevops Substack post (Grade C); any future upgrade of the embedding model requires full reindex; no automatic detection
- **Agentic "search tool" per planner step increases average latency from 4.8s to 32.4s and tokens from 1.8K to 27.2K** — Supermemory blog (https://blog.supermemory.ai/latency-budgets-memory-retrieval/) (Grade C); giving the LLM a retrieval tool violates vQA's ≤2-node-per-loop constraint and blows the latency budget
- **AC-parse-time classification misrouting is permanent for that session — a wrong module assignment at parse time means the correct helper is never retrieved** — educative.io routing patterns (Grade C); classifier accuracy is the critical gate; no fallback once routing is done
- **Chunking at file level for large helper files (QO_helpers.ts is multi-KB) produces embeddings averaged across all functions, making individual function retrieval unreliable** — TDS "Your Chunks Failed" post (https://towardsdatascience.com/your-chunks-failed-your-rag-in-production/) (Grade C); function-level chunking is required but adds index complexity
- **Switching embedding model mid-lifecycle forces full corpus rebuild; picking the wrong model initially is an expensive migration** — ragaboutit.com "Embedding Model Selection Crisis" (Grade C); lock-in begins at index time

### Open Questions

1. **CPU latency with ONNX-optimized sentence-transformers or quantized CodeBERT**: The 450ms/query baseline from sbert.net is for unoptimized CPU inference. ONNX or int8 quantization reportedly cuts this by 40%+. No practitioner measured this specifically for code embedding models (voyage-code-2, CodeBERT) on Docker/ECS CPU — the actual per-query latency for vQA's ~200K token corpus (indexed) is unknown.

2. **Voyage asymmetric retrieval for per-step latency**: Voyage's asymmetric approach indexes with the high-quality model and queries with a tiny local model. No practitioner post was found describing this in a Docker/ECS/no-GPU context. Would this reduce query latency enough to be viable for vQA?

3. **ChromaDB cold-start workaround**: The ~1 minute first-retrieval latency in ChromaDB is a known issue (LlamaIndex #15201). No post was found describing a production fix (pre-warm strategy, persistent index vs in-memory, ECS task definition tuning) for this specific scenario.

4. **Hybrid BM25+dense recall improvement on code corpora at vQA's scale**: The 69% error reduction cited for hybrid retrieval is on general text RAG, not code RAG at ~200K tokens with function-name lexical mismatch. Whether the improvement carries over to the specific vQA failure mode is unknown without an empirical eval (DRP-001).

5. **AC-parse-time classifier accuracy threshold**: No practitioner post quantified the acceptable misrouting rate for a parse-time classifier. At what error rate does misrouting cause more failures than per-step retrieval latency costs? This is a DRP-001/DRP-002 question.
