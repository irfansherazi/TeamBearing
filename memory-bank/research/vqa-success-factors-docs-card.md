### TRAP Candidates

**TRAP-1: LangGraph `recursion_limit` default is opaque and not a public constant**
The default `recursion_limit` value is set inside LangChain's `RunnableConfig`, not in LangGraph's public API surface. The source confirms the value must be >= 1 and raises `ValueError` if not, but the actual default (25 in LangChain convention) is not published in the official LangGraph docs and was not accessible via the docs site (redirects loop). If vQA graph invocations omit `recursion_limit` in the config, the effective limit depends on whichever RunnableConfig default the installed LangChain version applies — a hidden constraint that could change between LangChain minor versions. TRAP candidate because it is a silent, version-dependent constraint on every graph execution.

**TRAP-2: LangGraph version 1.2.3 is yanked — merging strategy regression**
PyPI records a withdrawn release (1.2.3, 2026-06-01) for an "unintended merging strategy regression." If vQA is pinned to 1.2.3 exactly (or if pip resolved it before the yank), state channels in multi-node graphs may accumulate or merge values incorrectly, causing non-deterministic agent state — a root cause for ghost-passing or infinite-loop behavior. TRAP candidate because the regression directly affects the pattern (multi-node state accumulation) that is the subject of this spike.

**TRAP-3: Extended thinking `budget_tokens` deprecated on Opus 4.6 / Sonnet 4.6; returns 400 on Opus 4.7+**
Official docs explicitly state: `budget_tokens` is deprecated on Claude Opus 4.6 and Claude Sonnet 4.6; it is not supported (returns 400 error) on Opus 4.7+, Fable 5, Sonnet 5, and Opus 4.8. Adaptive thinking replaces it. If vQA uses extended thinking via `budget_tokens` on any of these model versions, the API call will fail mid-run with a 400. TRAP candidate because an in-flight agent failing mid-chain on a 400 would appear as a budget-cap or circuit-breaker event in logs, masking the true cause.

**TRAP-4: Playwright action/navigation timeouts have no default — runs can hang indefinitely**
Playwright's official timeout documentation confirms that action timeout and navigation timeout have **no built-in default** (unlike test timeout at 30 s). Without explicit `actionTimeout` and `navigationTimeout` configuration, any stuck SPA transition blocks the agent indefinitely, consuming action budget tokens while waiting. TRAP candidate because this is a likely structural contributor to the high circuit-breaker rate on SPA navigation steps.

**TRAP-5: Pydantic `constr()` / `conint()` / `confloat()` deprecated, removed in v3.0**
Official Pydantic type docs mark the `con*` shorthand functions as "discouraged" and scheduled for removal in Pydantic v3. Any vQA schema using these types will produce deprecation warnings on current Pydantic v2 and will break on v3 upgrade. TRAP candidate because a Pydantic v3 upgrade (triggered by any dependency update that pins pydantic>=3) would break LLM output validation schemas silently at import time.

### Open Questions

1. **What is the exact default `recursion_limit` value in the LangChain `RunnableConfig` for the version pinned in `requirements.txt`?** The LangGraph docs site serves redirect loops (all langgraph.github.io paths redirect without serving content). The source confirms the parameter exists and that a value >= 1 is required, but the numeric default could not be confirmed from official docs. Recommend checking `langchain_core.runnables.config.RunnableConfig` source for the pinned `langchain-core` version.

2. **Is vQA currently pinned to the yanked LangGraph 1.2.3?** The Internal/Codebase lane should cross-check `requirements.txt` or `pyproject.toml` for the exact LangGraph version. If so, upgrading to 1.2.9 is urgent.

3. **Which Claude model ID does vQA use on Bedrock, and does it use `budget_tokens` for extended thinking?** If the model is Opus 4.6 or Sonnet 4.6 with `budget_tokens`, the extended thinking calls are deprecated; on Opus 4.7+, they return 400. This needs to be confirmed against the codebase's Bedrock invocation configuration.

4. **Does vQA's `playwright.config.ts` set explicit `actionTimeout` and `navigationTimeout`?** If not, any navigation or action that blocks will hang until the LangGraph `recursion_limit` or the agent's budget cap fires, not until Playwright times out — creating a false causal picture in logs.

5. **Does the Angular SPA under test register a service worker?** If yes, Playwright's network interception via `page.route()` may silently miss requests, producing ghost-passing test steps where the SW serves cached responses. The mitigation (`serviceWorkers: 'block'`) must be evaluated for compatibility with the app's auth flow.

6. **Does vQA use prefill (partial assistant message) in any of its prompts?** If yes and the model version is Sonnet 4.6 or Opus 4.6+, those calls return 400. The structured outputs replacement path (or `strict: true` tool schemas) should be validated before any model upgrade.

7. **Is server-side compaction viable for vQA's LangGraph-orchestrated chain?** Compaction is a Bedrock/Anthropic API feature; LangGraph's checkpointer tracks state at the graph level, not conversation-message level. Integrating compaction into a LangGraph tool node would require custom tooling to pass the compaction block through the state channel and reconstruct messages correctly. Open question for the Architecture lane.
