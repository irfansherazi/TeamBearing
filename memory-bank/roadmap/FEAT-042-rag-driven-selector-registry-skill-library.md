### FEAT-042: RAG-Driven Selector Registry & Skill Library
- **Version**: next
- **Status**: complete
- **Priority**: high
- **Complexity**: Level 4
- **Description**: The vQA system prompt currently embeds the full Selector Registry (selector_registry.json) and Skill Library (skills/*.yaml, blueprints/*.yaml) as static XML blocks on every LLM call, regardless of which selectors or skills are actually relevant to the current AC step. This inflates prompt size by thousands of tokens, degrades model attention on long runs ("lost-in-the-middle" degradation), and raises per-run cost unnecessarily. This feature replaces the static injection with an aggressive RAG retrieval layer: at planning time, the AC step text and enriched domain context are used to query a pre-built vector/BM25 index over both the Selector Registry and Skill Library; only the top-K most relevant entries (target: ≤20 selectors + ≤5 skills) are injected into the prompt, replacing the current full-dump strategy. Design decisions required: (1) Index architecture — single unified index vs. two separate indices (selector vs. skill), embedding model choice (local sentence-transformers vs. API-based), hybrid BM25 + dense retrieval vs. BM25-only to avoid API cost; (2) Chunking strategy — how to represent a selector entry as a retrieval unit (full JSON object as one chunk vs. split by field), how to represent a skill/blueprint (full YAML vs. sub-step chunks); (3) Query construction — how to derive the retrieval query from the AC step (raw text, enriched domain XML, target element name only, or LLM-generated retrieval query); (4) Top-K tuning — optimal K for selectors vs. skills without dropping critical context (benchmark against baseline prompt with full registry); (5) Index lifecycle — when to rebuild (on KB update, on new selector_registry.json commit, CI hook), warm-up vs. lazy-load at engine start; (6) Fallback strategy — if retrieval confidence is below threshold, fall back to a broader category filter rather than full dump; (7) Prompt budget enforcement — hard cap on total injected context (e.g., 2000 tokens for selector+skill section vs. current ~8000 token average), measured and enforced at runtime. Phased implementation: Phase 1 — Index Build & Offline Pipeline (chunker, embedder, BM25 indexer, serializer for both registry and skills, triggered by KB update hook); Phase 2 — Retrieval Integration (query builder, hybrid scorer, top-K selector, inject into planner prompt, replace static XML blocks); Phase 3 — Prompt Budget Enforcement & Benchmarking (token counter for injected sections, hard cap enforcement, A/B benchmark: RAG prompt vs. static prompt on 20 diverse AC steps — measure pass rate, token count, latency); Phase 4 — Index Lifecycle & Observability (rebuild trigger on registry change, warm-up at engine start, RAG retrieval stats surfaced in HTML audit report: tokens saved, entries retrieved, retrieval latency). Success metrics: ≥ 50% reduction in selector+skill prompt section token count vs. current static baseline, ≤ 2% degradation in AC step pass rate (retrieval must not drop critical selectors), index rebuild time ≤ 30s on full registry (~300 selectors + ~50 skills), retrieval latency ≤ 50ms per step (must not add perceptible latency to the decision loop), retrieval stats surfaced per-run in the HTML audit report.
