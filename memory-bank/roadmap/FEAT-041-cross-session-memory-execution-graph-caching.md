### FEAT-041: Cross-Session Memory & Execution Graph Caching
- **Version**: next
- **Status**: planned
- **Priority**: high
- **Complexity**: Level 4
- **Description**: Every vQA run currently starts from scratch, forcing the agent to re-solve complex, vague setup steps (deep module navigation, multi-step form setup, auth flows) for every ticket. This feature introduces Cross-Session Memory with two orthogonal capabilities: (1) Execution Graph Cache — when vQA successfully navigates a complex flow, it serializes the topological action graph (ordered list of navigation steps with selectors, URLs, and post-conditions) and the browser session state (cookies + localStorage snapshot) to a persistent store. Future runs whose preconditions semantically match a cached graph can fast-forward: the agent restores the session state directly via Playwright's `storageState` API and injects the cached URL, skipping the LLM-driven navigation entirely. (2) Card Intelligence Cache — relevant metadata extracted from previously-processed Jira cards (domain, AC structure, enrichment context, KB articles retrieved, execution outcomes) is persisted keyed by card ID + AC hash. Future runs on the same card or semantically similar cards retrieve this intelligence without re-querying Jira or re-running the enrichment pipeline. Design decisions required: (1) persistence backend — local JSON/SQLite vs. shared Redis vs. filesystem blob store; must be zero-infrastructure for local dev but extensible to shared CI; (2) graph identity key — how to fingerprint a navigation flow for cache lookup (URL prefix + AC domain + module hash vs. LLM-generated semantic embedding); (3) precondition matching — similarity threshold for "close enough" graph reuse vs. exact match only; must handle minor UI topology shifts without cache poisoning; (4) session state replay fidelity — which cookies/localStorage keys are safe to restore vs. which are stale/session-scoped and must be re-acquired (auth tokens vs. UI preferences vs. CSRF tokens); (5) card intelligence schema — what fields to capture per card (AC steps, domain tags, enrichment XML, KB article IDs, step outcomes, failure diary); (6) cache invalidation — TTL-based expiry, version-hash-based invalidation when KB is updated, and manual flush command; (7) privacy/security — ensure no PII or auth credentials are persisted in plaintext; token fields must be excluded from session snapshots. Phased implementation: Phase 1 — Persistence Layer (storage backend abstraction, session state serializer, graph serializer, card intelligence schema); Phase 2 — Graph Capture (post-successful-run serialization hook, precondition extractor, cache writer); Phase 3 — Cache Retrieval & Fast-Forward (precondition matcher, session state restorer via Playwright storageState, fast-forward executor path); Phase 4 — Card Intelligence Cache (Jira card metadata persister, AC hash deduplication, retrieval integration in ac_parser_node); Phase 5 — Cache Management (TTL eviction, invalidation on KB update, CLI flush command, cache stats in HTML report). Success metrics: ≥ 60% of repeated-module runs successfully fast-forward (skipping navigation LLM calls), avg run setup time reduction ≥ 50% on cached flows (LLM tokens saved on navigation steps), card intelligence cache hit rate ≥ 80% on re-runs of the same Jira card, zero cache-poisoning incidents (session restore causing wrong UI state) across 50 test runs.
