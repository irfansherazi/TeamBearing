## System Overview

vQA runs as three deployed containers — the Python/FastAPI backend that hosts the full AI execution engine and REST/WebSocket API, a Redis data store that provides optional distributed run state, and a React SPA served separately as a static build. The backend is the dominant unit: it embeds LangGraph, Playwright/Chromium, the Knowledge Base RAG system, S3 storage, and Jira integration into a single image built from `docker/Dockerfile`. Redis is a managed add-on used when horizontal scaling is needed. The React frontend is an inferred container (no compose service yet) served as a static Vite bundle.

## Operational Notes

### Ops Scripts (Not a Container)

The `ops-scripts` component (`scripts/`, `dedup_kb.py`, `conftest.py`) is **not deployed as a container**. It is standalone operational and maintenance tooling run on-demand from a developer workstation or CI pipeline. It interacts with S3, Bedrock, and the Jira API directly. See [`components/c4-component-ops-scripts.md`](./components/c4-component-ops-scripts.md) for the full inventory of scripts.

### CI Variant

`docker/docker-compose.ci.yml` declares a second variant of `vqa-backend` (named `vqa-ci`). It uses the same Dockerfile but skips supervisord, disables noVNC, and sets `VQA_MODE=headless`. This is NOT a separate C4 container — it is an operational variant (environment overlay) of the same `vqa-backend` image. The CI variant has no Redis dependency in its compose file, meaning run state defaults to in-memory in CI contexts.

### .github/workflows/vqa-test.yml (CI Cross-Reference)

The GitHub Actions reusable workflow (`vqa-test.yml`) consumes a pre-built `vqa:latest` image as a service container. It does not build images — it is an orchestrator that references the `vqa-backend` image produced from `docker/Dockerfile`. No new container types are introduced by this workflow.
