## Decision

**Chosen**: Option A — Pre-Parsing Vision Enrichment (Asynchronous & Parallel)

The agent will automatically scan for and analyze relevant image attachments *immediately after* fetching the Jira ticket context but *before* the Stage 1 BDD Normalization. This ensures that the visual context is available as a first-class input to the normalization process, allowing the LLM to resolve ambiguities in the AC text using actual visual evidence from the ticket.

---

## The Journey: From Attachment to BDD

### 1. Ingestion Phase (The "Eyes" Open)
- **Trigger**: `JiraClient.fetch_ticket_context(ticket_id)` is called.
- **Discovery**: The client retrieves metadata for all attachments.
- **Selection**: The agent filters for "high-value" attachments:
    - MimeTypes: `image/png`, `image/jpeg`.
    - Size: < 5MB (to avoid latency).
    - Limit: Max 3 most recent images.
- **Action**: The agent downloads the selected attachments in parallel.

### 2. Analysis Phase (The "Visual Brain")
- **Parallel Processing**: Each image is sent to the `VisionAnalyzer`.
- **Instruction**: "Analyze this Jira attachment. Identify UI components, labels, and workflow indicators that clarify the Acceptance Criteria. Focus on resolving terms like 'the button', 'the dropdown', or 'the form' mentioned in the AC."
- **Output**: A concise text summary of the visual facts (e.g., "The 'Submit' button is actually labeled 'Place Order' and is located in the bottom-right of the 'Checkout' modal").

### 3. Normalization Phase (The "Context Integration")
- **Injection**: The combined summaries from all analyzed images are packaged into a `<visual_context>` XML block.
- **Stage 1 BDD**: The `ac_parser_node` passes the raw AC + `<visual_context>` to the BDD Normalizer.
- **Result**: The produced BDD scenario uses the precise labels and locations found in the images, reducing Stage 2 compilation failures and execution-time "element not found" errors.

## User Touchpoints & Feedback

### Developer/Operator Experience
- **Logs**: The developer sees clear logs about which attachments were found, which were analyzed, and any that were skipped due to cost/size limits.
- **Audit Report**: The HTML audit report includes a section "Visual Context used for Planning" with the text summaries generated by the Vision LLM (and potentially thumbnails of the analyzed images).

### HITL Integration
- If the Vision analysis is highly ambiguous or contradictory to the text, the agent may flag a "Context Conflict" and prompt the user during the planning phase, though this is a Phase 4 enhancement.

## Success Scenario: The "Ambiguous Button"

1. **Jira AC**: "Click the primary button to save the record."
2. **Problem**: There are three buttons: "Save", "Submit", and "Commit". Which is "primary"?
3. **Attachment**: A screenshot shows the "Save" button highlighted in blue (the theme's primary color).
4. **Vision Analysis**: "The primary action in the screenshot is a blue button labeled 'Save'."
5. **BDD Output**: `When I click the "Save" button` (instead of `When I click the primary button`).
6. **Execution**: Playwright finds `role=button[name="Save"]` immediately. **PASS.**

## Risk Mitigations

| Risk | Mitigation |
|---|---|
| **Cost** | Filter by mimeType and size; strict limit of 3 images per ticket. |
| **Latency** | Parallel downloads and analysis calls. |
| **Hallucination** | Vision prompt instructs the model to only report what is explicitly visible and to mark uncertain items as `<inferred>`. |
| **Privacy** | Only attachments from the specific Jira ticket being tested are accessed. |
